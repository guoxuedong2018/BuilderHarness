# PRD / FRS 产出

在 `docs/features/<MMDDHHMM>_<MODULE>_<NAME>/` 下产出需求件套。模板在
`docs/templates/`，方法论在 `docs/WORKFLOW.md`。

## 核心原则：件套自洽

新人拿到这个目录，不翻别的文档，就能理解：

- 要做什么；
- 边界在哪；
- 怎么算做完；
- 还有哪些问题没定。

达不到就是没写完，不进入下一步。

## 范围

PM / Agent 产出：`FRS.json`、`README.md`、`FLOW.md`、`STATE.md`（按需）、
`ACCEPTANCE.md` 空模板。原型代码归业务工程；本 Skill 不直接改业务实现。

## 步骤

1. **先形成设计依据。** 先用 `builderharness context "<任务>" --json` 找相关来源，再读现状源码、已有需求和用户最近确认的决定；UI 任务按需要读路由。
   核查历史前提与反例，允许新目标修订旧决定。建议和未决假设不写成已确认规则；非 UI 项目不虚构页面或路由。
   M/L 需求按 `.agent/skills/requirement-review/SKILL.md`「M/L：形成设计依据」完成「意图 → 现状 → 目标 → 用户任务 → 位置/数据对应 → 反例走查」，写进需求 README。
2. **FRS.json。** 从 `docs/templates/FRS.json` 复制，填：
   - `goal` / `background` / `scope.include` / `scope.exclude`
   - `spec`：按页面 → 功能点 → 显示/交互/取值/权限，写法见下文〈规格怎么写〉
   - `shots`：截图配方；写之前先跑 `npx builderharness capture-shots --probe <路由>` 看页面上有哪些选择器可用
   - `acceptance`：可测试、逐条编号；功能点用 `ac` 回指
   - `verification` / `openQuestions` / `dependencies`

   `background.problem` / `background.solution` 是 PRD「需求背景」两段的来源：先讲目前的问题，再讲产品方案怎么解决，别揉进 `goal` 一句话。一条要再分几点时写 `{ "text": "…", "children": ["…"] }`。
   `scope.include` 说边界（做什么、不做什么），`spec` 说规则——研发只读后者，不能靠前者反推。
3. **README.md。** 从模板复制，填需求背景、待决清单、本轮设计依据、验收标准、文件导航。
   待决清单按「谁来定」分组，空着 = 还没定；只放真有第二种可能的条目，明显只有一个答案的留在决策表。
   与 `openQuestions` 对应的条目只写一句索引，完整表述留在 FRS.json，同一段话不在两处各写一遍。
4. **FLOW.md。** 画核心用户旅程；异常分支（无权限、空数据、超时、取消）也要画。
5. **STATE.md。** 只有多状态流转才保留；简单 CRUD 删除，并删掉 README 文件导航里对应的行。
6. **ACCEPTANCE.md。** 先建空模板，验收阶段逐轮填写。

## 规格怎么写

### 四类规则各管什么

| 分类 | 管什么 |
|---|---|
| `display` 显示规则 | 由数据决定的显示条件：什么情况下出现、不能操作、要提醒，只写条件；长什么样、文案在原型源码里 |
| `interaction` 交互规则 | 操作之后后端发生什么：写入什么、校验什么、状态怎么变、失败如何处理 |
| `value` 取值规则 | 数据来源与范围、枚举值、默认值、排序、搜索匹配方式、计算口径 |
| `permission` 权限规则 | 哪个角色隐藏或禁用。单独成类是因为它最容易漏，PRD 里渲染成黄底高亮 |

空的分类整个省略，不写「无」。每个功能点标 `origin`，按线上实测标，不凭印象：

- `online`：线上已有、本期不改；
- `online-hardened`：线上已有，本期改了交互或校验；
- `online-page-new`：页面线上已有，这块功能是新加的（新页签、新步骤、新区块）；
- `new`：新页面、新模块，或线上没有的数据与能力。

页面在不在、这块在不在分开看；一个功能点里两种都有就拆开。PRD 按它给功能点打标签，`--scope delta` 只出研发要迭代的那几类。

### 前端看得到的不写

原型源码整份交给研发，研发按页面、按接口开发。判据只有一个：**只拿到页面源码、没有 mock 数据的研发，能不能知道这件事。** 能就不写；只在 mock 里实现的过滤、计算、状态流转要写。

| 删（源码里就有） | 留（前端看不到） |
|---|---|
| 位置、顺序、分栏、卡片、有哪些列、用弹窗还是抽屉 | 数据从哪来、范围（工作区、状态、时间）、过滤、排序、默认值、枚举 |
| 界面文案原文：标题、按钮、占位、ⓘ、空态、确认框、提示条 | 计算口径：算法、换算、阈值、哪些不进计算、条数怎么数 |
| 点哪里打开什么、跳到哪页、悬停看全、切页签、地址栏参数、本地记住的草稿与偏好 | 状态枚举与流转：什么条件进哪个状态、谁触发、停止或失败后怎样 |
| UI 规范已统一的：空状态、翻页器、筛选即时生效、禁用加原因的形式 | 校验与约束：保存时拦什么、唯一性、创建后不能改、上下限、同时只能有一个 |
| 颜色、字号、加粗、提醒色 | 保存什么、记在哪个对象上、版本怎么升；对下游的影响；权限；调用外部服务（超时、重试、调用记录） |

一句里界面和逻辑混着时，删掉界面、留下条件。以 BuilderHarness 示例原型（实验列表、运行、评审）为例：

- 「运行中的实验【删除】置灰，悬停写原因（还在跑，先停掉再删）」→「删除条件：实验下没有运行中的运行；不满足时仅可停止。」
- 「「本周运行数」卡片右上角显示环比，涨了是绿色向上箭头」→「本周运行数的环比：本周一 00:00 起的运行数对上周同期；上周同期为 0 时不出环比。」
- 「新建实验弹窗关掉再打开，填过的内容还在」→ 整条删（本地草稿，前端可见）。
- 「没有实验时显示一句引导；筛选后没有结果时换一句」→ 整条删（UI 规范统一）。
- 请求体示例、导出文件格式这类代码块是接口契约，**留**。

显示规则剩得很少是正常的。一个功能点删完什么都不剩，留下它在原型里不显眼、研发容易漏的那一条；实在没有，就问用户这个功能点还进不进 PRD。

### 一条一句，总起句加子条

研发按条实现、按条对验收，所以一条规则一句话，能单独成立、单独验收。一句里用分号串了几件事就拆开；列举、几种情况、几个字段，先写以「：」结尾的总起句，下面用 `children` 分子条，最多三级。别处写过的规则不复述，写「见「功能点名」」。

### 规则体，不是说明文

每条写成「对象 + 条件 + 结果（+ 作用范围）」，用规范术语，不用口语（这个、就、照常、跟着、一起）。只写「是什么、怎么算」，不写「为什么这么考虑」、不举例——理由留在 README 决策表；一条规则要配解释才读得懂，是规则本身没写清。界面文案「说用户的话」是另一回事，不搬进规格。

- 「实验开跑以后再换数据集，分数也不会跟着变」→「运行开始时锁定所用数据集版本；之后数据集发布新版本，已开始的运行不变，仅对新运行生效。」
- 「停掉的运行就别再算进成功率了，因为它没跑完」→「成功率 = 已通过的运行数 ÷（已通过 + 失败的运行数）；已停止的运行不计入分子与分母。」

### 没人定过的规则不写

原型上显示了什么不等于是规则。从页面、mock 推出来的细节（如「评审队列按更新时间倒序」）先问有没有人定过，没有就删，拿不准的进 `openQuestions`。

### 排版记号与特殊规则

照常写中文即可，PRD 渲染时自动生效：

| 写法 | 渲染 | 用在哪 |
|---|---|---|
| `【动作】` | 加粗 | 按钮、文字链 |
| `「元素」` | 加粗 | 字段、筛选项、页签、状态名 |
| `{$变量}` | 灰色 | 文案拼接里的占位符 |
| `==重点==` | 加粗飘色 | 研发会想改、改了就破坏设计意图的约束 |
| `“文案”` | 斜体灰字 | ⓘ 里的界面文案，和规则正文分开读 |

`==重点==` 省着用：一屏里超过两三处就等于没有重点，只留给「看起来多余、其实是唯一护栏」的条款（如「停止运行时==保留已产生的结果==」）。

- 规则中间插截图：`{ "shot": "<截图 key>" }`；
- 结构化示例（请求体、导出文件、字段格式）：`{ "code": "…", "lang": "json" }`，跟在它说明的那条下面，不在一句话里列一长串字段；
- 人在已发布文档里插的图同步回来：`{ "image": "<imageId>", "width": 宽, "height": 高 }`，照原样放回；插在分组「参考图」格里的写进这一组的 `shots`，和截图 key 按先后混排。精简规格时它跟着最近那条留下的规则走，不丢。

## 规则的来源：事实先于推测

`spec` 里每条规则都要说得出来源：线上实测、产品确认或需求规格。推测出来的规则总是比实际更严、更多。

- **迁移既有能力**时，先查已有现状记录；没核实的关键行为列入 `openQuestions`，它的答案是事实，不能用「建议按 Y 实现」代替。
- **示例文件只说明格式，不说明规则。** 示例里某列为空，可能是不需要，也可能是那天没填。
- **DOM 里有不等于是现状**；**mock 只是占位**，原因、取值、默认值不能从 mock 归纳；**字段名不等于语义**，从字段名推出来的用途标成推测进 `openQuestions`。
- 给建议时标明是推的还是问来的；没有建议的问题会被原样退回，PM 要的是一个可以被推翻的默认值。
- 问来的事实只问一次：记进项目已有的事实记录（带日期与来源），下次先查那里。

## 校验

```bash
npx builderharness check-frs <KEY>
```

硬失败必须修：AC 引用不存在、功能点没有 AC、四类规则全空、路由不在
`src/config/frs-map.js`、截图 key 未定义。提醒项（未被覆盖的 AC、未引用的截图）
要在 README 里处理或说明。

## 边界

- `FRS.json` 是 PRD 的真源；PRD 是它的渲染视图，不手写第二份正文。
- 不把未确认的技术方案写成需求规则。
- 原型截图只作为参考图；知识库步骤图走 `docs/kb/shots.config.mjs`。
- 状态改动同步 README 头部和 `FRS.json.status`；转「已确认」由人拍板。
- 最近的决定替代旧规则时，同步检查 scope、spec、AC、FLOW/STATE 和原型；不靠删验收项掩盖实现缺口。
- 评审结论每条都落到 FRS/README，不无声丢弃；其中研发会想改、改了就破坏设计意图的，内联成对应功能点的一句约束——决策表本身不进 PRD。

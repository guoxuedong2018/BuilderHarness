# 将产品理念转成设计判断

案例来自本项目；可迁移的是判断标准，不是固定页面形式。

## 1. 筛选面板收起后还留一条窄栏

局部修补会反复改箭头、颜色、竖排文案与间距。先问收起后的核心任务：用户希望把空间还给结果区，并仍能找回筛选。由此考虑把展开入口放进已有工具栏，恢复整块列表空间。这个结论适用于当前已有工具栏的列表；不能推成所有侧栏都必须删除。

## 2. 一条 Case 有两个视频，还要 GSB 和各自分数

分清四层：Case 是输入与聚合视角；推理结果是可被单独评价的对象；指标声明结果语义与类型；评估器执行判断。一个分数仍是数值，多个结果用对象关联表示，不因为在 Case 下聚合就把所有指标定义成 JSON 类型。

GSB 是比较语义，枚举是取值类型，评单条或评一对是目标范围，HTTP 一次传几条是调用契约。这些有约束关系，但不应无条件绑定。GSB 可以作为快捷预设；不能因此推出只有 GSB 才能评价一对，或所有混合指标服务都一次返回完整结果。

人工按 Case 交一整份作业、分析按指标查询原子结果，可以由同一事实的不同视图承载。逻辑拆分不自动要求新建一个「评分记录管理」菜单。

## 3. 自动化评估创建页

业务评测人员通常先决定评哪批结果、想知道什么；若当前使用者确实按固定服务包操作，评估器优先也可能合理。先验证角色与场景，再决定顺序。

采用指标优先时，指标行直接表达评价对象和选用的评估器；只有存在多个有效候选时再要求选择。适用性判断须包含状态、版本、输入和指标范围，不能用数组中第一项代替业务默认值。

高级调试页可以显示 HTTP 请求与原始响应；日常任务创建页中的「每条视频一行」通常应改成能理解的结果示例。记录行数属于实现细节，不能承担解释业务的职责。

## 4. 人机协作有两种模式

「机器评完，人抽样复核」与「机器预标一部分题，人完成全部题」的差别包含题目覆盖、送标范围、结果来源，不是仅将抽样率设为 100%。用同一条 Case、多个指标、机器只会部分指标的场景验证，避免一个开关加一个比例冒充两种工作流。

## 5. 模型调试成功不等于用户任务完成

登记评估器至少要能保存、回到列表找到它、重新打开检查配置；设为可用后，状态和下游候选须变化。原型无需真实调用 HTTP，但模拟结果要受配置和输入影响，不能无论选了什么都返回固定的成功值。

## 6. 范围与语义变更

最近讨论改成指标优先，FRS 仍写评估器优先时，应明确待采纳的方案或同步更新相关规则与 AC。不能在文档写一种、原型做另一种后统称已完成。

人工分数与机器分数都落在 0–1，并不自动意味着衡量同一概念。归一化只改变数值尺度；跨指标、跨 rubric 的可比性仍需要业务依据。不因增加一个换算控件就宣称能计算可靠的人机一致率。

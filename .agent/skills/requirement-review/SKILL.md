# 需求判断与评审

先判断方案是否成立，再决定流程重量。沿用宿主项目指引、权限和既有 harness。

## 1. 获取任务相关证据

- 先明确用户想改善的结果，区分目标与用户提出的实现方案。
- 用 `builderharness context "<任务>" --json` 读取相关指引、决策、规格、源码与验证入口；本地安装可用 `npx --no-install builderharness context "<任务>" --json`。CLI 不可用时使用项目搜索，不静默下载其他版本。
- 核查引用原文、作用域、日期和适用前提。材料可能冲突、过期、缺失或被截断；上下文输出不能替代原文与实际检查。
- 分开说明：人的意图、已记录约束、观察到的实现、未经验证的推断。历史决定、Agent 和人的新方案都可以被新证据质疑。

## 2. 判断标准

逐项按任务需要检查，不生成通用总分：

1. 目标与因果：谁在什么场景遇到什么问题？方案为什么改善它？
2. 当前约束：是否冲突于仍然有效的业务规则、接口契约和项目边界？引用具体位置。
3. 历史前提：旧决定为什么成立？目标或条件是否已经变化？
4. 替代与成本：能否复用现有能力，以更少概念、状态、操作和维护成本实现同一目标？
5. 反例与验证：什么证据会推翻判断？能否通过更小、可逆的变更或实验验证？

输出四类结论之一，并解释适用依据：

- **可以推进**：范围明确且无已知冲突，按足够轻的流程直接工作。
- **当前方案冲突**：明确当前有效约束及实际后果，暂不按原方案修改，提出满足原目标的替代路径或重评约束的办法。
- **建议替代方案**：比较同一目标下的收益、成本与代价；个人偏好不能作为拒绝依据。
- **证据不足**：明确缺口，先调查或提出最小实验；只问真正阻塞的问题，不因缺数据一律否决或升级流程。

用户明确改变产品目标时，可以修订旧决定，保留替代关系和取舍。不要用历史记录永久否决新需求，也不要把 Agent 的建议写成用户已确认的事实。

## 3. 流程重量

| 级别 | 判据 | 后续 |
|---|---|---|
| S | 明确的文案、样式、局部修复或小改 | 直接实施并补相关验证，无需全套 FRS 或额外确认 |
| M | 单个行为或模块变更 | 形成足够的目标、范围与验收说明，复用项目现有文档；UI 原型按需要 |
| L | 跨模块、新核心概念或广泛影响 | 明确边界与设计依据后再实施；已授权范围内持续推进，真正的产品语义分歧才交给人选择 |

已有 FRS 工作流可继续使用 prd-author；非 UI 项目无需虚构页面或路由。证据缺失先补证据，不自动要求全套文档。

## 4. 回复与完成

小改动允许一句判断后直接执行。有实质分歧时，用简短结构说明：**目标 / 结论 / 证据与反证 / 推荐路径与代价 / 验证或待定点**。引用项目路径和位置，避免把实现方案当成已确定的需求。

运行相关检查后区分通过、失败、跳过、未运行、零测试及覆盖不足。检查命令存在不代表已执行；测试通过只证明执行的断言。不能自动改规格来掩盖实现冲突。

只对长期有效且由人确认的取舍追加决策：背景、目标、适用前提、替代方案、代价、证据、重新评估条件，以及替代的旧决定。优先使用已有决策文档；无需为每次小改生成记录。保留旧记录，建议与假设保持未确认状态。

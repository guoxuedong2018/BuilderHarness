# 把产品理念变成设计判断

案例用 BuilderHarness 示例原型（实验列表、运行、评审）的场景写；可迁移的是判断方法，不是固定的页面形式。

## 1. 筛选面板收起后还留一条窄栏

局部修补会反复改箭头、颜色、竖排文字和间距。先问收起的目的：用户想把空间还给结果区，同时还能找回筛选。由此考虑把展开入口放进已有的列表工具栏，让整块列表空间回来。这个结论适用于已有工具栏的列表；不能推成所有侧栏都该删——承担持续导航的侧栏是另一种任务。

## 2. 一次运行产出两个候选回答，要各自打分，还要比哪个好

分清四层：实验运行是输入与聚合视角；每个候选回答是能单独被评价的对象；指标声明结果的语义与类型；打分服务执行判断。一个分数仍然是数值，多个结果靠对象关联表示，不因为在运行下聚合就把所有指标定义成 JSON。

「两两比较」是比较语义，枚举是取值类型，评单个还是评一对是作用对象，一次请求传几条是调用契约。它们有约束关系，但不应无条件绑定：比较可以是快捷预设，不能因此推出只有比较类指标才能评一对，或所有服务都一次返回全部结果。

人按运行交一整份评审、分析按指标查原子结果，可以是同一份事实的两个视图。逻辑拆分不自动要求新建一个「评分记录管理」菜单。

## 3. 新建运行页先选什么

使用者通常先决定比哪批结果、想知道什么；如果当前使用者确实按固定的服务组合操作，先选服务也可能合理。先验证角色与场景，再定顺序。

采用指标优先时，指标那一行直接表达评价对象和选中的服务；只有存在多个有效候选时才要求选择。适用性要看状态、版本、输入和指标范围，不能拿数组第一项当业务默认值。

接入调试页可以显示原始请求与响应；日常的新建页里「每条结果一行记录」应换成看得懂的结果示例。记录行数是实现细节，不承担解释业务的职责。

## 4. 人机协作有两种模式

「机器评完、人抽样复核」与「机器只评一部分项、人补齐全部」的差别在覆盖范围、送人工的范围和结果来源，不是把抽样比例调到 100%。拿同一次运行、多个指标、机器只会其中几项的场景验证，避免一个开关加一个比例冒充两种工作流。

## 5. 调试成功不等于用户任务完成

登记一个打分服务，至少要能保存、回到列表找到它、重新打开检查配置；设为可用后，状态和新建运行页里的候选都要跟着变。原型不必真发请求，但模拟结果要受配置和输入影响，不能无论选什么都返回同一个成功值。

## 6. 范围与语义变更

最近的讨论改成指标优先，规格还写着服务优先时，要么明确待采纳的方案，要么同步更新相关规则与验收；不能文档写一种、原型做另一种，然后统称已完成。

人工分数和机器分数都落在 0–1，不代表衡量的是同一件事。归一化只改尺度；跨指标、跨评分标准的可比性需要业务依据。不因加了一个换算控件，就宣称能算出可靠的人机一致率。

# 已有 Agent 接入与基于项目证据的需求判断

> 状态：实现已落地，真实宿主验收受阻；详见 [验收记录](./ACCEPTANCE.md)
> 创建日期：2026-10-28（Asia/Shanghai）
> Feature Key：10282122_AGENT_WORKFLOW
> 分级：L — 涉及初始化、项目上下文、需求评审、依赖分发和现有宿主兼容。

## 需求背景

用户认可 BuilderHarness 把产品意图与历史取舍留在仓库中的价值，希望在已有 Codex / Claude Code 项目里直接使用。当前入口以 Vite 演示和完整脚手架为主，需求评审偏重流程分级，核心工具和浏览器依赖一起安装。

本次优化的目标是：用户通过一次初始化，让现有 Agent 在真实任务中找到相关背景、检查需求依据、必要时反对当前方案并提出替代路径，然后实施与验证。人的设计决策也需要接受证据、反例和替代方案的检验。

本文件保留设计依据、实施拆解和验收标准。2026-10-29 用户授权一起实施 A–F；代码、技能和迁移工具已落地。自动化与真实宿主的结果分别记录于 ACCEPTANCE.md，不建立虚构页面路由来适配现有 FRS 检查，也不把受阻的行为验收标为通过。

## 讨论中已认可的方向

- 保留用户现有 Agent、harness、项目规则与工作流。
- 用户入口收敛到现有 `builderharness init`，也可以在本地 Agent 中用一句自然语言发起；内部检查无需变成一组必学命令。
- 脚本执行可重复的检查与证据收集，当前本地 Agent 负责解释上下文、比较方案和完成后续工作。
- Agent 可以质疑人的方案；反对理由需要项目证据，并尽可能提供满足原目标的更好路径。
- 长期保存意图和决策，按任务获取当前事实，用可执行证据检查行为约束。版本与变化提示作为辅助。
- 基础能力与浏览器评审、媒体、桌面集成分离，使实际安装成本与所选能力对应。

## 用户任务与预期体验

1. 用户在已有项目的 Codex / Claude Code 会话中说：「初始化 BuilderHarness，沿用项目现有规则和工作流。」
2. Agent 调用 `builderharness init`，读取已有项目约定并接入所需指引，给出简短的接入结果与能力边界。
3. 用户照常提出一个真实改动。Agent 查找目标、相关决定、当前实现和验证入口，判断方案是否成立。
4. 对明确且低风险的任务直接推进；对有依据的冲突指出分歧并给出替代方案；对关键未知先查证或提出最小验证。
5. 实施后报告实际验证结果。只有产生了值得长期保留的设计取舍时，才补充决策记录。

首轮使用不以补齐全项目 FRS、启动 Vite、修改应用入口或连接模型 API 为前提。标准流程在已有 Agent 会话内完成；独立终端运行初始化只能完成可确定的配置工作，不能被描述成已经启动 Agent 或完成语义评审。

## 设计依据

### 1. 需求判断在流程分级之前

判断依次关注：用户想改善的结果；方案与结果的因果关系；当前有效约束；历史决定的适用前提；复用机会与长期成本；可能推翻方案的反例和最小验证方式。标准不做成通用总分，Agent 的偏好也不能当成项目约束。

输出按证据区分四种结论：

| 结论 | 行动 | 必需依据 |
|---|---|---|
| 可以推进 | 选择足够轻的实现和验证流程 | 目标与范围明确，未发现需要先解决的冲突 |
| 当前方案冲突 | 暂不按原方案修改，说明如何调整方案或修订约束 | 引用具体、当前适用的约束及冲突后果；同时检查其前提 |
| 建议替代方案 | 比较能达到同一目标的路径，说明成本与代价 | 项目能力、相关决定或可验证的影响，不把个人喜好当证据 |
| 证据不足 | 先调查、最小实验，或提出一个真正阻塞的问题 | 明确缺什么、缺口影响什么；不自动升级为否决或 L 级全套流程 |

简短任务允许简短结论。确有分歧时，输出至少包含：目标、结论、证据与反证、建议方案、代价和验证方式。人可以基于新目标修订旧决定，Agent 需要明确发生了什么变化，而不是用旧文档永久否决新需求。

### 2. 任务相关的证据，避免维护另一份项目事实副本

上下文收集结果包含来源路径与位置、适用范围、事实/意图/推断的区别、证据局限和可用验证入口。已有文档优先引用，不强制复制进新的知识库；项目没有历史决策时明确说明缺失，不能补造理由。

默认从项目指引、用户指定文件和相关改动范围出发，按任务补充源码、规格与决定。设置可检查的文件数和内容预算；达到预算、遇到不可读路径或来源冲突必须显示。生成目录和依赖缓存不作为默认扫描对象。

读取配置和 package scripts 是发现验证入口；实际执行检查由当前 Agent 在既有任务授权与项目规则下完成。证据采集本身不能把仓库描述中的命令当作可自动执行的指令。引用材料也不覆盖宿主指令和权限。

### 3. 初始化的默认动作足够少

默认接入只增加必要的入口指引和评审技能，发现多个文档体系时复用有效入口。工程实现可以保留内部的完整 scaffold 模式供新建项目使用，普通用户无需选择一系列模式或手工串联命令。

对已有文件采用明确归属的托管片段，保留片段外内容、文件格式及用户改动。目标内容被用户改过、标记损坏或技能同名冲突时，保留原内容并说明具体冲突，不猜测覆盖。未完成的步骤和恢复动作要可见，不能以「初始化成功」掩盖部分失败。

宿主接入方式必须按实际版本验证：Codex / Claude Code 分别检查其项目指引与技能加载约定；不能把 `.agent/skills` 文件存在、MCP 注册成功或生成配置成功等同于 Agent 已加载并遵循流程。

### 4. 决策记录保存依据与演进

记录重要决定的背景、目标、适用前提、考虑过的替代方案、代价、证据与重新评估条件。用户确认产生的长期取舍才进入共享记录；Agent 建议和未决假设保持显式标记。改变历史决定时新增替代关系并保留原记录。

源码变化只提示可能受影响的证据；测试结果只证明执行过的断言范围。实际报告区分通过、失败、跳过、未运行与无覆盖，不用绿色总状态暗示需求完全成立。改代码后自动把规格改成代码现状，不能作为解决冲突的默认动作。

## 范围

本轮计划包含：任务相关的项目证据收集；需求评审技能升级；现有 `init` 的轻量接入；已有 harness 与文档的合并；重要决策和验证结果的延续；依赖分离；Codex / Claude Code 的真实流程验收与迁移文档。

后续独立考虑：在终端自动拉起 Agent 的宿主适配；Next.js / Nuxt 浏览器内评审与 AST 插件；自动语义漂移判定；全量代码索引服务；新增桌面控制台；外部发布。基础能力可用于这些项目，不代表浏览器集成已支持这些框架。

## 实施拆解（建议顺序）

下面的工作包是可分别审阅的实现单元。代码位置表示实施范围，实际交付与验收以 ACCEPTANCE.md 为准。A–D 组成首个可试用闭环；E–F 完成轻量分发与面向外部用户的验收。

| 工作包 | 具体交付 | 主要位置 | 依赖 | 完成标准 |
|---|---|---|---|---|
| A · 项目与任务证据 | 提取可复用、无 UI 依赖的读取模块；扫描已有指引、文档与验证入口；支持任务范围、来源引用和读取预算 | `pipeline/lib/paths.mjs`、`integrations/host/src/project.mjs`，新增共享模块 | 无 | 非 Vite、无 docs 和 monorepo 夹具均可运行；缺失、截断、冲突可见；CLI 与 MCP 适配使用相同读取结果 |
| B · 需求判断技能 | 把目标、有效约束、历史前提、替代方案和反例置于 S/M/L 之前；保留轻任务出口；本仓库与 scaffold 技能保持一致 | `.agent/skills/requirement-review/`、`scaffold/.agent/skills/requirement-review/`、相关工作流 | A 的证据约定 | 场景评审能指出具体依据、反证和代价；支持接受需求、反对当前方案和承认未知；不以反对次数衡量质量 |
| C · 单入口接入 | 升级 `init`；检测实际宿主约定；按归属合并指引；重复运行、部分失败恢复与移除接入可控；迁移桌面完整 scaffold 调用 | `pipeline/init.mjs`、`bin/builderharness.mjs`、`scaffold/`、`integrations/desktop/main.cjs`、`scripts/test-scaffold.mjs` | A、B | 已有 AGENTS/CLAUDE 与技能不被覆盖；两次执行无重复；移除接入保留用户知识；默认不写应用入口、路由表或依赖声明；旧 scaffold 流程可验证 |
| D · 决策与验证延续 | 初始化之后使用真实任务完成「判断→实施→验证→必要时记录新决定」；明确决策引用、替代关系和未验证状态 | `docs/DECISIONS.md` 模板、评审/编写技能、任务证据模块 | B、C | 新目标可合理推翻旧决定；持久记录与临时证据分开；失败、跳过、零测试和未运行不会报告为验证通过 |
| E · 安装依赖边界 | 将基础 CLI/读取/可选 MCP 与浏览器 UI、AST、媒体和桌面依赖分离；保持用户 init 入口；补分发与迁移验证 | `package.json`、锁文件、exports/bin/files、`vite.mjs`、`integrations/`、依赖检查脚本 | A、C 的接口 | 干净目录安装基础能力不带 React、Mermaid、XYFlow、Babel、Vite；安装所选浏览器能力后原演示与生产边界检查通过；打包产物无本机路径或未解析内部依赖 |
| F · 真实宿主与发布验收 | 验证 Codex 和 Claude Code 的实际加载、任务执行与重开会话；演练迁移；重写现有项目接入文档 | 集成测试与场景材料、`README*`、`docs/getting-started*`、`integrations/host/README.md` | D、E | 两种宿主分别保存真实运行证据；不把协议测试替代宿主验收；非 Vite 项目完成一次真实改动，应用配置保持原有工作方式 |

建议依赖顺序：`A → B → C → D`，`A + C → E`，`D + E → F`。第一批实现先完成 A–C，并在本仓库用一个真实需求检验；D 的关键验证在对外试用前完成。E 可以在接口稳定后推进，但在完成前不宣传基础安装已轻量化。

| AC11 | 干净目录安装基础能力的依赖树符合 E 的边界；记录安装体积、耗时、依赖树和实际执行结果，同口径对比基线 | E |

## 验证与发布边界

- A/C/E 以可失败的自动化检查覆盖读取、文件保护、兼容和依赖边界；验证真实打包安装，不只在源码 checkout 中运行。
- B/D 使用带预期证据与反例的场景，以及本仓库的一次真实任务；规则文件存在不算 Agent 行为通过。
- F 单独记录宿主名称、版本、初始项目状态、加载证据、实际检查结果及尚未覆盖的能力。两种 CLI 已实际探测；安装与登录状态不能代替宿主行为验收。
- 修改相关实现后运行适用的集成/scaffold 检查、`npm run check`；涉及浏览器与拆包时增加 `npm run build:demo`、产物 preflight 和发布适配边界测试。
- 本轮已实施代码与技能并执行适用检查；两个真实宿主因网络或认证条件受阻，尚未完成行为验收。没有发布 npm 版本。

## 待决事项与风险

| 事项 | 当前建议 | 处理节点 |
|---|---|---|
| 首版具体默认接入文件与宿主技能路径 | 沿用宿主当前官方加载约定，最小增量接入；既有约定不明确时显示有限能力，不假装已加载 | C 设计与宿主验证 |
| `init` 默认行为变化与旧调用迁移 | 保留完整 scaffold 能力，先迁移已知调用，再切换默认入口；版本说明明确说明变化 | C、F |
| 包名称、版本和现有 import 路径迁移 | 保留用户的主 CLI 入口；先验证真实打包与兼容成本，再定具体包名；不为拆包放松公共依赖检查 | E |
| Agent 提出的判断与人的决定冲突 | 提供依据、替代方案和需要重评的前提；产品语义变更仍需人确认，历史决定和 Agent 都可被新证据质疑 | B、D |
| 用户不希望增加文档负担 | 优先引用已有材料，只把实际发生且长期有效的取舍写入共享记录 | A、D |
| 真实模型行为不稳定 | 用多类场景和真实任务检查证据质量；一次成功不宣传所有需求都能正确判断 | B、F |

工程方案和优先级在本草案中可继续调整。需要改变产品语义或现有用户兼容方式时，应明确呈现相应差异，不把内部实现选择升级成新的用户操作负担。

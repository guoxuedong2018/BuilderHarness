# PRD 发布

FRS 件套是真源，PRD 是它的一个渲染视图。**不要手写 PRD 正文**——写进 `FRS.json` 的
`background` 与 `spec`，让命令渲染；手写的那份下次迭代就和 FRS 对不上了。

渲染、截图、建文档、追图、写正文、回读、回写 `prdDocId` 全在一条命令里：

```bash
npx builderharness prd <KEY> [--scope delta]          # 只出计划，不写目标端（等同 dry-run）
npx builderharness prd <KEY> [--scope delta] --yes    # 人确认后外发
npx builderharness prd <KEY> --yes --absorb           # 目标端里人的改动已同步回 FRS（或确定不要）后再发
npx builderharness prd <KEY> --yes --redline          # 大改先出修订稿给人过目，确认后不带 --redline 再发定稿
npx builderharness prd <KEY> --yes --folder <目录 id>  # 新建时建在目标端的这个目录下
```

不要绕过它手拼发布适配器的命令；外发统一经 `BUILDERHARNESS_PUBLISH_GATEWAY` 配置的适配器。

## 前提

- `npx builderharness check-frs <KEY>` 通过；
- 需求状态已是「已确认」或用户明确要求预览：草案发给研发会被当成定稿实施；
- 发布目标已通过 `BUILDERHARNESS_PUBLISH_GATEWAY` 配置；没有配置时不要伪造发布结果。

## 步骤

### 1. 规格写对

没有 `spec` 就先补，不能从 `scope.include` 或 `acceptance` 反推——前者是边界、后者是断言，反推出来的规则必然有漏项和编造。写法见 `.agent/skills/prd-author/SKILL.md`〈规格怎么写〉：四类规则各管什么、前端看得到的不写、一条一句、规则体、没人定过的不写。

README 的决策表不进 PRD；其中研发会想改、改了就破坏设计意图的少数几条，内联成对应功能点规则里的一句约束。

### 2. 渲染并通读

```bash
npx builderharness export-frs-prd <KEY>
```

产物在 `docs/prd/<KEY>/`（构建产物，不入库）。先读 `preview.md` 过一遍；发现的问题回 `FRS.json` 改，不改产物。

**发布前逐条自查。** 每条规则过四问，有一问答「是」就回 `FRS.json` 改：

1. 研发不看这条也不会做错？——删。
2. 有口语、原因、举例，或在复述界面？——按规则体重写，理由回 README 决策表。
3. 别的功能点已经写过？——留一处，另一处删掉或写「见「功能点名」」。
4. 是从原型或 mock 推出来、没人定过？——问用户，拿不准的进 `openQuestions`。

这一步靠判断，不做成自动检查：口语词清单误报多，漏的又恰是「读着通顺、其实没有依据」的那种。

**要「精简版」时收窄范围，不压缩结构。** `--scope delta` 只渲染 `origin` 为 `new` / `online-page-new` / `online-hardened` 的功能点，章节、四类规则与真源都不变；不砍章节、不另写摘要。

### 3. 出计划，人点头再发

```bash
npx builderharness prd <KEY>
```

不写目标端：校验、渲染、截图，再和目标端比，打出这一版要做什么。把计划**原样摘给用户**，连同目标、密级和分享范围一起问清楚；用户点头后加 `--yes` 再跑一次。

- **新建**（`FRS.json` 没有 `prdDocId`）：建文档、追图、写正文、回读核对四节，`docId` 自动写回 `prdDocId`。新文档的分享范围请用户在目标端设；用户给了目录就加 `--folder <目录 id>`。
- **更新**（有 `prdDocId`，永远更新这一篇，不另建）：只补功能点表里变了的段落，图没变就复用。计划里 `~` 是「目标端现在 → 本地要改成」，`-` 是要删、`+` 是要加。
  - **目标端里有人改过**：命令和上次发布的底稿逐段比，把人改了什么写进 `docs/prd/<KEY>/cloud-edits.md`——在哪个「分组 · 功能点 · 规则类别」下、第几级、原文和现文、FRS 里有没有（配图带 imageId 与宽高）。补丁不动人改过的段落，人删掉的也不加回；这层保护一直保留到 `--absorb`。照清单处理：
    1. 要留的改回 `FRS.json`（保留用户的原话与层级）；和这一轮决定冲突的不同步，回复里说明；
    2. 再出一次计划，清单里剩下的「FRS 里没有」都应该是有意不要的；
    3. 人确认后加 `--absorb` 发布：底稿换成目标端现状，那些段落才按 FRS 改写或删掉。**删用户改过的段落前先问用户**，不要自己加 `--absorb`。
  - **「没有上次发布的底稿」**：分不清哪些是人改的，计划里的改写与删除会落到目标端现状上。先把目标端那边要留的改动同步回 FRS 再出计划；发过一次之后就有底稿了。
  - **大改先出修订稿**（整组规则改写、一次几十条以上）：`--yes --redline` 不落定稿——删掉的、改之前的原文划线标红留在原位，改写按相似度配对、紧跟其后、浅绿底，新增的也浅绿底；原样重跑不会重复划线或插入。请用户在目标端逐条过目。确认后先出一次不带 `--redline` 的计划：划线的按删除、浅绿底只去底色；用户在修订稿上改过、或去掉删除线想保留的，照常列进 `cloud-edits.md`，同步回 FRS 再发定稿。小改（几条规则）直接发定稿。
  - **「需求背景 / 方案设计和目标端不一样」**：命令只同步功能点表，这几段去目标端手改；确认没人改过可以 `--yes --rewrite` 整篇覆盖——会抹掉所有人工修改，先问用户。
- **停下来的几种情况**：件套校验没过、原型没起、截图选择器失效、发布适配器报错——按提示修好重跑，不绕过。

补丁按批提交（每批最多 50 个操作，相邻删除合并），每批先试跑；上次追图后中途失败留在文末的临时图，下次发布时自动认出并删掉。

人在原型里改过文案时，先把改动同步回 `FRS.json`，再出计划。

## 边界

- 不把内部域名、账号、密钥写进仓库。
- 不手写 PRD 正文，也不改 `docs/prd/` 下的产物——下次导出就被覆盖。
- 不用 Markdown 通道发正文：在线文档不渲染 Markdown 里的 Mermaid，功能点表格的嵌套列表、黄底高亮与内联图也会被压平。
- 不把 `openQuestions` 写进 PRD；开放技术问题留在 `FRS.json`，在设计评审上当面过。
- 发布失败时保留本地构建产物；不要静默重试到线上，也不为省事 `--rewrite`。
- 发布计划与目的地适配器 UI 在 dsh 面板 / Studio 中查看；命令行只负责确定性构建。

出正式交付计划前先看 `builderharness verify <KEY> --status`。阻断项处理后重新出计划，
对照当前 FRS、截图和目标端版本确认。沿用已有的增量更新与人工编辑保护。

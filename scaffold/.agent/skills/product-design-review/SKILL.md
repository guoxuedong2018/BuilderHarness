# 产品设计与原型准备

原型用于验证产品方案。先读根目录 AGENTS.md 的设计哲学，再按本技能形成设计结论；组件选择和代码编辑在这些结论之后。用户明确要求的工作阶段决定本轮范围。

## 1. 恢复意图与有效决定

先判断本轮是讨论、评审、规格修订还是实现。只要求评审时给问题、证据和推荐；已要求实现时，设计结论明确后继续执行，不逐阶段等批准。

读取相关 FRS、需求 README、现有页面与对象定义、最近相关决定。区分用户确认、已核实的现状、模型建议和未决事项。历史决策按第 6 节检索并确认当前效力；当前代码也可能只是未完成的原型，不能自动当成产品现状。

在既有需求 README 的「本轮设计依据」记录：谁要在什么场景完成什么、目前的困难、完成后的结果、本轮范围与最近纠正。还没有件套时先在回复给出这段依据，建件套时迁入同一处；不新增一套记忆文件。原型返工不得直接把现有代码当作设计起点。

## 2. 映射现状与目标领域

M/L 需求先完成 [设计依据模板](references/design-brief.md) 的领域映射。简单且不改变对象或流程的 S 级修改可跳过；已有映射仍有效时只补本轮差异。

对受影响的核心概念说明：

- 现状叫什么、负责什么、在哪里查证；目标要承担什么职责。
- 身份与粒度：一条代表什么，谁拥有，是否有版本；关键关系及状态变化。
- 复用、调整还是新增，以及原因。代码里的相似字段不等于同一业务对象。
- 该概念是用户需要理解的对象，还是只应存在于实现中的机制。

新实体不自动对应新菜单、新页面或新物理表。字段取值类型、对象范围、执行协议与页面分组分别判断，再说明约束关系。可以提出候选数据结构和技术方案，但将尚待研发确认的契约、存储或性能问题标明，不能声称已经实现。

用一个主场景和一个能推翻简单设计的反例检验模型；按实际复杂度补充，不为凑数量造边界。判据是：业务结果能否表达、对象会不会混淆、未来已知增量是否迫使本轮核心概念重造。

## 3. 从用户任务推导交互与位置

先串起入口、操作、结果、返回或恢复，再决定页面、抽屉、两栏和组件。对存在真实取舍的结构，比较沿用现状加增量与可行替代方案，给推荐、代价和可能推翻推荐的条件。

对关键元素记录「位置与数据对应」：用户此刻要判断什么、属于哪个对象、取值或状态从哪里来、改动影响什么、放在哪里及为什么。不需为每个装饰元素填表。

- 顺序依照判断的依赖；频繁对照的信息共同可见；短时选择结束后回到原任务。
- 核心关系在需要它做判断的地方可见，不要求每条关系在两侧列表各加一列。
- 失败和禁用原因紧邻受影响对象；高级登记和调试信息按角色与时机分层。
- 保存、试跑、发布状态等不同动作，各有明确结果；成功提示不代表状态已经改变。
- 主任务决定布局，再用现有组件实现；不能从“已有两步表单”“已有抽屉”反推业务只能这么做。
- 无关区域保持基线；本轮需求改变的步骤和布局可以列入 Delta。新证据出现时允许调整形态，记录理由与受影响规则。

必要时给简短文字布局草图。只输出可审阅的判断、取舍和证据，不输出内部思维过程，也不以重复产品理念代替具体方案。

## 4. 用场景检查是否可以编码

在首次产品代码编辑前，核对当前设计是否满足以下条件，并在 README 用简短结论指向具体证据：

1. 现状到目标的映射有来源；新对象和新增限制有理由，推测没有冒充事实。
2. 主任务可从入口到结果；关键反例可表达，关键状态与恢复方式没有靠猜。
3. 影响判断的元素有位置与依赖理由，读写的数据和后续状态对得上。
4. 当前决定与 FRS 的 scope、spec、AC、相关 FLOW/STATE 一致；实现缺口没有被改规格消掉。

缺哪项就先补哪项；不能只写四个“通过”。不影响本轮页面与业务语义的技术问题可留在 openQuestions，使用明确的合成数据继续。涉及范围、核心语义或主流程且无法可靠判断的问题，给出推荐后请用户决定；已经回答过的不重复问。

用户授权实现时，以上依据成立即进入 `builderharness-ui-prototype`，无需额外审批。用户只要方案或 review 时，不擅自写产品代码。用户明确要求一个小范围探索性原型时，标明要验证的假设和范围，不把探索结果直接定为正式规格。

## 5. 实现、验证和反馈回流

沿用原有 FRS schema 和发布器：规则在 FRS，设计理由在 README，实际验证在 ACCEPTANCE。新讨论替代旧规则时，更新受影响内容；只写一次完整事实，其余使用引用。

数据可以模拟，行为必须自洽：用户输入影响后续展示，保存后可查，状态变更影响下游，重试针对实际失败。明确模拟边界，不用固定成功结果掩盖未实现项。

实现后读取 `.agent/skills/frontend-quality/SKILL.md`：运行 `cd web && npm run check`，在浏览器走通主路径与关键恢复，检查控制台并目视截图。记录「场景 → 操作 → 预期 → 实际 → 证据」。静态检查通过不能代替页面和体验验收；没有环境就如实写未验证。

收到“看不懂”“没抽象好”等实质纠正时，按第 6 节校准判断再继续已授权修改；不预设问题只需补引导，也不预设必须重做结构。

设计判断困难时按需读 [对照案例](references/examples.md)。案例提供判断方法，不是所有未来需求的固定答案；本技能不默认委派其他 Agent。

## 6. 从反馈积累可复用判断

### 开始：调用仍然有效的经验

- 用本轮用户任务、业务对象和设计问题检索 `docs/DECISIONS.md`（例如 `rg -n '筛选|收起|窄栏' docs/DECISIONS.md`），阅读相关条目全文，再搜索同主题的后续修订。关键词命中只是入口，不以第一段“决策”为最终结论，不默认全量加载。
- 核对状态、来源、适用场景及“同日定稿”等补充。部分被取代时分清保留与废止的部分；较新日期不自动代表更高效力。用户当前明确决定与历史冲突时，按其授权范围更新受影响内容；冲突不明且影响核心方案时，给出推荐并澄清。
- 在既有 README「本轮设计依据」简述实际采用的经验：原条目的日期/标题、为何适用、具体改变了本次什么选择。无需凑条数；没找到就如实说明，不能声称已经读取。页面形式相似但任务不同的，说明差异，不照搬。

### 被纠正：校准判断后再修改

当用户实质否定理解、方案被推翻或同类问题重复出现时，用几句话说明：上一版优化了什么、用户反馈指向什么目标、哪个假设需要修正、方案因此怎样改变。依据用户原话或可观察结果，区分概念、流程、位置和文案问题；不要输出冗长自我检讨或内部思维过程。

仅有“看不懂”等模糊反馈时，可以给出有依据的诊断，但标为待核实，必要时只问影响方案的关键分歧。普通文案修改或新范围不自动算成设计错误。方向明确后继续已授权工作，无需为复盘另等批准。

### 结束：只保存新增且可追溯的结论

- 当前需求的规则与理由回到 FRS/README；平台事实进入已有事实记录；跨需求、可迁移的判断才写入 `docs/DECISIONS.md`。使用该文件模板，保留原方案、纠正依据、当前结论、适用边界和来源。用户明确要求只读时，仅在回复给出待记录内容。
- 用户明确决定可以记录为有效；模型自行归纳的经验标为候选。未反对、采纳一次局部修改或模型自评通过，都不等于用户确认全局偏好。当前动作可以修正，尚未验证的经验不升级为全局约束。
- 写入前查重：同一事实引用原条目；有新证据就补充；决定改变则新记一条，并在旧条开头注明哪部分被哪条取代。旧正文保留，不批量改写历史。不为没有新增信息的轮次增加日志，也不每次改动都扩写 AGENTS。
- 候选经验在后续不同场景得到明确反馈时，再更新其适用范围与状态；只将有依据且稳定的判断提炼到现有设计哲学或对应技能。无法核实的来源不编造，不把长期未反馈当作通过。
- 对重要或反复出现的偏差，复用或补充 `references/product-design-cases.json` 中的场景，保留一个适用例和一个不应照搬的反例；一般小修不新增用例。以之后是否少了同类纠正、减少结构性返工、完成真实任务衡量效果；没有运行的只记待验证，不用反思字数或自评分证明进步。
